## R-20260918-17 — OrchBench: evaluate orchestration plans separately from worker quality

- **SOURCE:** “OrchBench: Evaluating Multi-Agent Orchestration Plans in Isolation via Deterministic Simulation,” arXiv:2607.25656.
- **SOURCE_DATE:** 2026-07-28.
- **PROBLEM:** End-to-end multi-agent evaluation conflates orchestration quality with worker capability, tool reliability, and environment noise; adding more agents can look useful even when coordination quality degrades.
- **CORE_IDEA:** Represent work as a dependency DAG and evaluate assignment, information transfer, retention, makespan, and token cost in a deterministic simulator. The paper reports strong correlation with real Claude Code execution while using much less execution cost, and finds that preserving task-critical information matters more than merely increasing agent count.
- **AMADEUS_CURRENT_STATE:** The Control Plane already models task dependencies, WRITE_SET separation, leases, and a fixed concurrency target; D01 already owns observability/durable-orchestration research. Current acceptance correctly does not equate worker activity with progress.
- **REAL_GAP:** A future orchestrator evaluation harness could test whether a proposed allocation preserves critical dependency information and avoids coordination overhead before real workers execute. This is an evaluation gap, not a reason to increase concurrency or invent more tasks.
- **PROPOSED_DELTA:** Fold this source into `AUTO-20260918-D01` as comparative evidence for deterministic orchestration-plan simulation and information-retention checks. Do not create a separate implementation task in this run.
- **RISKS:** Simulation can omit real tool/provider failures; benchmark task DAGs may not match Amadeus governance; optimizing makespan can conflict with evidence and safety; simulated quality must not become acceptance authority.
- **LICENSE:** Paper/code reuse license was not independently verified in this run. No code or dataset import is authorized.
- **EVALUATION_METHOD:** Synthetic Control Plane scenarios with explicit dependencies, WRITE_SETs, stale leases, review gates, and information-transfer requirements; compare plans on correctness-preserving completion, conflicts, blocked-state handling, and coordination cost. Real GitHub evidence remains the execution truth.
- **DISPOSITION:** `FOLD_INTO_D01`; no new READY task.

## R-20260918-18 — Stale inherited constraints need freshness/supersession signals separate from relevance

- **SOURCE:** “When Stale Constraints Go Unchecked: Budgeted Verification Failures in Inherited Agent Memory,” arXiv:2608.25553.
- **SOURCE_DATE:** 2026-08-26.
- **PROBLEM:** An agent can inherit a consolidated memory containing a constraint that was once valid but has since been superseded; relevance alone does not guarantee that the current authoritative record is checked.
- **CORE_IDEA:** Model immutable provenance and changing currentness separately. The paper reports large reductions in stale-consistent decisions when a fixed verification budget is reallocated toward the critical provenance path, suggesting freshness/supersession signals should be distinct from relevance.
- **AMADEUS_CURRENT_STATE:** B01 already identified growth-basis freshness as a narrow real gap and demonstrated a module-boundary probe around corrections; RuntimeStore/retrieval already preserve correction/supersession structure. B02 separately studies forgetting/deletion fidelity.
- **REAL_GAP:** No additional gap distinct enough from B01 is established here. The paper strengthens the case that freshness verification should be evaluated independently of ranking/relevance when a derived growth basis or inherited constraint may have changed.
- **PROPOSED_DELTA:** Add as comparative evidence to B01 review and any later authentic assembled-runtime freshness experiment. Do not open a second stale-memory implementation task.
- **RISKS:** The intervention assumes knowledge of a critical provenance path; verification budgets may differ in Amadeus; over-eager freshness checks can increase latency or suppress valid historical context.
- **LICENSE:** Paper/code reuse license was not independently verified in this run; no external implementation is imported.
- **EVALUATION_METHOD:** Paired fixtures where relevance is held constant while authoritative currentness changes through explicit correction/supersession; measure whether the active basis is revalidated before reuse and preserve the older record as history.
- **DISPOSITION:** `DUPLICATE_WITH_B01_SCOPE`; no new READY task.

## R-20260918-19 — MemIR: typed memory representation addresses provenance-role collapse

- **SOURCE:** “Mitigating Provenance-Role Collapse in Long-Term Agents via Typed Memory Representation,” arXiv:2605.25869.
- **SOURCE_DATE:** 2026-05-25.
- **PROBLEM:** Flat long-term memory can blur raw evidence, retrieval cues, derived claims, and factual authority, producing source-monitoring errors.
- **CORE_IDEA:** Use a typed memory intermediate representation that structurally separates evidence, cues, and claim atoms, then restrict factual authorization to supported claims with provenance-scoped use.
- **AMADEUS_CURRENT_STATE:** Amadeus already has stronger project-specific separations between source authority, runtime experience, admission, retrieval, Persona growth, and the PR #2 offline Claim/Evidence contract. Model-generated or retrieved text cannot become authority merely by being present.
- **REAL_GAP:** The source is useful as comparative evidence for typed retrieval/provenance evaluation, but it does not establish a missing second memory representation layer or justify replacing existing admission/provenance authority.
- **PROPOSED_DELTA:** Fold into B01/PR #2 review as a source-monitoring comparison. If future evaluation is added, test whether evidence, cues, derived claims, and authority are never collapsed during retrieval/projection.
- **RISKS:** A typed schema can create false confidence if type assignment is model-generated or wrong; an additional IR could become a parallel authority; schema complexity can hide provenance loss rather than prevent it.
- **LICENSE:** Paper/code reuse license was not independently verified in this run; no code import is authorized.
- **EVALUATION_METHOD:** Synthetic evidence/cue/claim mixtures with quotations, superseded facts, cross-entity material, and unsupported inferences; require deterministic provenance binding and explicit non-authority for cues/observations.
- **DISPOSITION:** `FOLD_INTO_B01_AND_PR2_REVIEW`; no new READY task.

## R-20260918-20 — Kontext: pre-action policy and sandboxing are distinct enforcement layers

- **SOURCE:** `kontext-security/kontext` GitHub repository; README and LICENSE inspected on 2026-09-18.
- **SOURCE_DATE:** Repository observed 2026-09-18.
- **PROBLEM:** Agent logs after execution do not prevent consequential actions, while a process sandbox and a semantic authorization policy answer different security questions.
- **CORE_IDEA:** Kontext inserts local policy at supported synchronous pre-action hooks, can deny matching actions before execution, and records agent/session/action/policy decision/outcome in an authorization ledger. Its documentation explicitly distinguishes semantic authorization from kernel/process sandbox containment.

The inspected Amadeus snapshot still lacks an integrated production tool executor.

- **PROPOSED_DELTA:** Add to A02 comparative references only. Do not install Kontext, add a production permission broker, or claim current tool enforcement from its existence.
- **RISKS:** Hook coverage varies by agent; unsupported actions may bypass policy; authorization ledgers can leak sensitive metadata; observe mode is not enforcement; a policy layer is not kernel isolation.

- **EVALUATION_METHOD:** A02 fixtures should distinguish prose-only rules, supported pre-action deny points, observe-only evidence, and independent sandbox containment. `ENFORCED` must cite the actual boundary for the specific action class.
