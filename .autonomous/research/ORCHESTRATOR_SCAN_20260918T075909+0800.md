## R-20260918-21 — DeepSeek provider readiness: ordered stream evidence is not remote-outcome reconciliation

- **SOURCE:** DeepSeek official API documentation: Responses API (`/responses`), Using the Responses API, Change Log, and Error Codes.
- **SOURCE_DATE:** Native Responses API support announced 2026-08-13; DeepSeek-V4.1-Flash released 2026-09-10; documentation rechecked 2026-09-18.
- **PROBLEM:** Current G6 is blocked on reliable long-generation provider readiness after two preserved `SUBMITTED_STATUS_UNKNOWN` outcomes. A reachability check or generic retry recommendation can be mistaken for evidence that a prior request did or did not complete remotely.
- **CORE_IDEA:** DeepSeek's current Responses API is explicitly stateless. It can stream semantic SSE events with monotonically increasing `sequence_number`; a normally received stream ends with `response.completed`, `response.incomplete`, or `response.failed`. However, server-side response/conversation storage, `previous_response_id`, and background recovery are not supported. In-connection progress evidence is therefore richer than a single opaque wait, but a dropped connection without an observed terminal event still does not provide authoritative remote-outcome reconciliation.
- **AMADEUS_CURRENT_STATE:** Current `provider.py` is journal-first: submitted status is committed before network I/O; remote failures after entering the HTTP path become `SUBMITTED_STATUS_UNKNOWN`; automatic paid retries are zero; repeating the same turn/slot cannot resend. The 9ad6063 G6 runbook preserves two UNKNOWNs (`N06_T4`, `N07_T3`) and explicitly says HTTP 401 reachability is not long-generation readiness evidence. The current endpoint remains Chat Completions; no endpoint migration is authorized by this finding.
- **REAL_GAP:** There is no independently established evidence that a fresh, bounded long-generation request on the current provider path can reliably reach an authoritative terminal outcome under the required timeout/configuration. There is also no documented DeepSeek server-side retrieve-by-response-id mechanism in the inspected stateless Responses API that would safely reconcile a disconnected UNKNOWN.
- **PROPOSED_DELTA:** Fold this into `AUTO-20260918-D01` and the existing G6 hold. Define a read-only provider-readiness evidence matrix that distinguishes DNS/TLS/connect, HTTP headers, first stream event, ordered progress, terminal event, local timeout, and remote-outcome status. Any future live readiness probe must be a separately frozen, unique, bounded scope; it must not reuse either UNKNOWN request, and it must not silently switch production endpoint semantics.
- **RISKS:** Treating partial SSE progress as proof of final completion; assuming a response ID is retrievable when the API is stateless; endpoint/model semantic drift; paying for a probe that is not required; credential or prompt leakage in telemetry; following generic 500/503 retry advice in a context where the prior remote outcome is unknown.
- **LICENSE:** Official provider documentation only; no external code or dataset is imported.
- **EVALUATION_METHOD:** First, deterministic offline mapping of provider stages to `NOT_SUBMITTED` / `SUBMITTED_STATUS_UNKNOWN` / authoritative terminal outcomes. Second, only if a future reviewed G6 scope explicitly permits it, use a new unique low-risk bounded request and require a captured authoritative terminal event plus journal binding; any transport loss after submission remains UNKNOWN. Never replay `N06_T4` or `N07_T3` and never infer completion from HTTP 401 or partial SSE events.
- **TASK LINK:** `AUTO-20260918-D01`; `HOLD-G6-07-CANONICAL` blocker refinement. No new task created.
